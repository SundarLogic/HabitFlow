# Architecture Decision Records

Short ADR log. Each entry: decision → rationale. Full detail of rules lives in [CLAUDE.md](../CLAUDE.md) §3.
Add new entries at the bottom; never rewrite an accepted decision. Supersede it with a new entry instead.

| # | Decision | Rationale | Status |
|---|---|---|---|
| ADR-001 | **Stack:** React (Vite) + TanStack Query + Tailwind / Node 20 + Express + PostgreSQL 16 + Sequelize, with Jest/Supertest, Vitest/RTL and Playwright. | Matches PRD §10. Mainstream, well-supported tools keep the first release simple. | Accepted |
| ADR-002 | **Auth = server-side sessions** with an opaque random token in an HttpOnly+Secure+SameSite=Lax cookie. Only the SHA-256 hash is stored. Logout deletes the row. The same token is accepted as a Bearer header. | Sessions can be revoked instantly (unlike JWT), a DB leak exposes no usable tokens, and the Bearer fallback serves the future mobile client. | Accepted |
| ADR-003 | **CSRF = double-submit cookie** (`csrf_token` cookie + `X-CSRF-Token` header) on all non-GET cookie-authenticated requests. | Cookie auth needs CSRF protection. Double-submit is stateless and simple for an SPA. | Accepted |
| ADR-004 | **Time:** TIMESTAMPTZ in UTC, calendar dates as DATEONLY `YYYY-MM-DD`, and "today" computed in the user's IANA timezone via Luxon. Server local time is never used. | Habits are calendar-day concepts. Server-local time causes off-by-one-day bugs across timezones. | Accepted |
| ADR-005 | **Completion uniqueness = UNIQUE(habit_id, completed_by, completion_date).** | Enforces one completion per day in the DB, not just the app. Including `completed_by` keeps the model ready for shared habits. | Accepted |
| ADR-006 | **Weeks = ISO weeks (Mon–Sun) in the user's timezone.** | One unambiguous definition for weekly targets, summaries and streaks. | Accepted |
| ADR-007 | **Streaks are derived from completion history on read.** Only scheduled days count. A pending today or in-progress week never breaks a streak. Weekly-target streaks are counted in weeks. | Satisfies the PRD rules: no punitive feedback, and historical edits recalculate automatically without stale cached values. | Accepted |
| ADR-008 | **Pending vs missed:** a day or week is pending until it ends in the user's timezone, then becomes missed if incomplete. | PRD §7: don't treat an in-progress period as failed. | Accepted |
| ADR-009 | **Completable dates:** `start_date ≤ date ≤ today`, the date must be scheduled for weekday habits, and the habit must be active. PUT and DELETE are idempotent. | Prevents future or invalid completions while allowing honest backfill. Idempotency makes retries and double-clicks safe. | Accepted |
| ADR-010 | **Retention:** DELETE archives by default. Permanent delete is allowed only for archived habits and cascades in one transaction. | Archiving preserves history (PRD §7). The two-step hard delete prevents accidental data loss and orphans. | Accepted |
| ADR-011 | **Active workspace via `X-Workspace-Id`**, defaulting to the personal workspace. Another workspace's resources → 404. | Workspace isolation from day one (PRD §2) with no extra work for single-user clients. 404 avoids leaking that a resource exists. | Accepted |
| ADR-012 | **Free plan = 10 active habits**, with limits stored in the `plans` table (JSONB) rather than code. | Entitlements can change without a deploy, and the model is ready for paid tiers. Billing is deferred. | Accepted |
| ADR-013 | **Layered backend:** routes → Zod validators → controllers (HTTP only) → services (logic + transactions) → models. | Keeps business logic testable and HTTP-agnostic, and gives one place for transactions and authorization. | Accepted |
| ADR-014 | **API conventions:** `/api/v1`, `{ data, meta }` collections, `{ error: { code, message, details? } }` errors, page limit ≤ 100, date ranges ≤ 366 days. | A consistent contract for web and mobile, with bounded queries that protect the DB. | Accepted |
| ADR-015 | **Schema changes via sequelize-cli migrations only.** UUID PKs, snake_case columns. | PRD §8: no automatic production schema alteration. UUIDs are safe to expose and distribute. | Accepted |
| ADR-016 | **Local Postgres via Docker Compose** with `habitflow_dev` and `habitflow_test` created by an init script. Credentials come from `.env`. | Reproducible setup. Tests never touch dev data, and no secrets live in git. | Accepted |
| ADR-017 | **Express 5 native async error handling.** No `asyncHandler` wrapper. | Express 5 forwards rejected promises from async handlers to the error middleware, so there is less boilerplate and no risk of forgetting the wrapper. | Accepted |
| ADR-018 | **Schema validation failures return 422 `VALIDATION_ERROR`** with `details: [{ location, path, message }]`. 400 is reserved for requests that can't be parsed (invalid JSON). This supersedes the "400 = validation" wording in the original API conventions. | One status for "understood but invalid input" makes clients simpler. The error `code` separates schema errors from business-rule 422s. | Accepted |
| ADR-019 | **sequelize-cli runs with `--options-path .sequelizerc.cjs`** through `npm run sequelize`. Migrations and seeders use `.cjs`. | The package is ESM (`"type": "module"`). Node ≥ 22 treats an extension-less `.sequelizerc` as ESM, which breaks the CLI's `require()`. `.cjs` works on every Node version. | Accepted |
| ADR-020 | **Seeders are not recorded and must be idempotent.** | `db:reset` (undo all → migrate → seed) and repeated `db:seed` always produce the same data, with no stale seeder bookkeeping after tables are dropped. | Accepted |
| ADR-021 | **One shared DB config (`src/config/database.cjs`)** used by both the CLI and the app. The app validates all env vars with Zod in `src/config/env.js` and refuses to start if any are invalid. | One source of truth for connection settings. Misconfiguration fails fast with a readable message instead of a runtime error. | Accepted |
| ADR-022 | **Test DB safety:** tests and `db:reset` only touch databases whose name ends in `_test`, enforced in three places. Test files run serially. | Truncation between tests is destructive. Serial runs avoid races on the shared database. | Accepted |
| ADR-023 | **Extra backend dependencies:** pg, pg-hstore, cookie-parser, pino-http, dotenv (runtime); nodemon, ESLint (@eslint/js, globals, eslint-config-prettier), Prettier, cross-env (dev). | Required drivers and infrastructure for the agreed stack: Postgres driver, cookie parsing for sessions/CSRF, request logging, env loading, ESLint flat config, and cross-platform scripts. | Accepted |
| ADR-024 | **Enum-like columns are `VARCHAR` + named `CHECK` constraints**, not native Postgres `ENUM` types. Allowed values for app code live in `src/models/constants.js`; migrations keep their own frozen copies. | Native enums need `ALTER TYPE` to change and are left behind by `dropTable`, which complicates `db:migrate:undo:all`. A CHECK can be swapped in one migration, and naming every constraint makes DB errors self-explanatory. Matches CLAUDE.md §4 ("CHECK constraints for enums"). | Accepted |
| ADR-025 | **FK delete behaviour:** child data of a workspace or habit is `ON DELETE CASCADE`. User references that represent authorship (`workspaces.owner_user_id`, `habits.created_by`, `habit_completions.completed_by`) and `workspace_subscriptions.plan_id` are `RESTRICT`. | Permanent habit deletion leaves no orphans (ADR-010), while a stray `DELETE FROM users` can never silently wipe history. Future account deletion must delete the personal workspace first, as CLAUDE.md §3.1 already requires. | Accepted |
| ADR-026 | **Plan `limits` / `features` JSON keys are camelCase** (`maxActiveHabits`, `historyDays`; `null` = unlimited). `pro` is active but marked `features.purchasable = false` until billing exists. Supersedes the `max_active_habits` example in the original §3.1 wording. | The JSON is returned to clients as-is, and API fields are camelCase (CLAUDE.md §5). A flag avoids a schema change for a billing concern that is out of scope. | Accepted |
| ADR-027 | **Schema additions beyond PRD §8:** `users.notification_preferences`/`last_login_at`, `sessions.ip`, `habits.color`/`icon`/`sort_order`/`archived_at`, `habit_completions.note`, a `habit_reminders` table, and `notifications.data`/`dedupe_key`. | Needed by first-release features (reminders, archiving, ordering) and by idempotent cron jobs (`dedupe_key`), without waiting for a later migration. | Accepted |
| ADR-028 | **Demo-data seeder** (`20261025000102-demo-data.cjs`) runs only when `NODE_ENV` is `development`. It throws under `production` and is a no-op under `test`. Rows use fixed ids and `ON CONFLICT DO NOTHING`; completions are chosen by hashing (habit, date). | Gives developers realistic data in one command, can never touch production, keeps `db:reset` on the test DB working, and stays idempotent (ADR-020). | Accepted |
| ADR-029 | **A workspace the user isn't a member of returns 404 `NOT_FOUND`**, the same as one that doesn't exist. This supersedes the 403 `WORKSPACE_FORBIDDEN` in the original §3.1 / ADR-011. A malformed `X-Workspace-Id` is still 422. | A 403 confirms that the ID exists, so workspace IDs could be probed. 404 for everything outside your memberships leaks nothing and matches the "never leak existence" rule for resources. | Accepted |
| ADR-030 | **Passwords:** 8–128 characters with at least one Unicode letter and one number. Stored as `bcrypt(base64(sha256(password)), cost 12)`. Login always runs one bcrypt compare (against a dummy hash for unknown emails). | bcrypt ignores input past 72 bytes, so without the pre-hash two 128-character passwords sharing a 72-byte prefix would both log in. The SHA-256 digest is 44 ASCII characters and covers the whole password. The dummy compare makes "unknown email" take as long as "wrong password". | Accepted |
| ADR-031 | **Sliding session expiry**, recorded at most once every 5 minutes: when a session is used and `last_used_at` is ≥ 5 min old, `last_used_at = now` and `expires_at = now + SESSION_TTL_DAYS`, and the cookie is re-sent with the new Max-Age. Expired sessions are deleted when presented, and nightly by `runSessionCleanup`. | Active users stay logged in and idle sessions die after the TTL. The 5-minute throttle avoids a DB write on every request. | Accepted |
| ADR-032 | **Account deletion is in first-release scope** (`DELETE /users/me`, password re-typed). One transaction deletes the personal workspace (cascade), then the user. If RESTRICT FKs block it (the user owns a team workspace or has history elsewhere), the whole operation rolls back with 409 `RESOURCE_IN_USE`. This supersedes "account deletion is out of first-release scope". | Users must be able to leave and take their data with them. The RESTRICT FKs from ADR-025 ensure deletion can never silently destroy other people's data. | Accepted |
| ADR-033 | **Rate limits:** login and signup share one limiter of 10 per 15 min keyed by IP (IPv6 /56) + normalised email. All of `/api` has 300 per 15 min per IP. Limiters are created per `createApp()` and kept in memory. | Per IP+email stops brute force on one account without locking out a whole office behind one IP. Per-app limiters keep tests isolated. A multi-instance deployment needs a shared store, and a deployment behind a proxy needs Express `trust proxy` (follow-up). | Accepted |
| ADR-034 | **CSRF scope and related error codes:** `csrfProtection` runs after `requireAuth` and checks unsafe methods on cookie-authenticated requests only (403 `CSRF_TOKEN_INVALID`). Signup and login are not CSRF-checked. They rotate the CSRF token. A wrong current password on password change or account deletion is 422 `INVALID_CURRENT_PASSWORD`, not 401. | Signup and login only accept `application/json`, which a cross-site form can't send and cross-site `fetch` can't send without a CORS preflight we reject. A 401 for a mistyped confirmation would make the SPA think the session ended. | Accepted |
| ADR-035 | **Habit PATCH semantics:** the body is merged with the stored habit and the result is validated by the same `habitStateIssues()` used on create. Fields not sent carry over only while `frequencyType` stays the same, so leaving `weekly_target` clears `targetPerWeek` and leaving `weekdays` deletes the schedule days. `status` in PATCH archives or restores. An archived habit may only change `name` / `description` unless the same request restores it, otherwise 409 `HABIT_ARCHIVED`. | One set of rules for create and update, with no client-side bookkeeping when switching schedules. Archived history stays stable while still allowing cosmetic fixes. | Accepted |
| ADR-036 | **Plan-limit checks lock the workspace row** (`SELECT … FOR UPDATE`) inside the create/restore transaction before counting active habits. | Without the lock, concurrent requests could both see 9 habits and create an 11th, as a test showed. The lock serialises creates per workspace only. | Accepted |
| ADR-037 | **Habit `startDate`** defaults to today in the user's timezone and may be in the past (backfill) but at most 1 year after today, otherwise 422. These checks live in `habitService` because they need the user and the clock. New habits get `sortOrder = max + 1`. Reorder is all-or-nothing: any id outside the workspace → 404 with no change. Lists use the standard `{ data, meta }` pagination. | "Today" depends on the user's timezone, so it can't be decided in a static Zod schema. Appending keeps a user's manual order. All-or-nothing reorder leaks nothing about foreign ids. | Accepted |
| ADR-038 | **Prorated first week for `weekly_target`:** when `start_date` isn't a Monday, the first week's target is `min(target_per_week, days from start_date to Sunday)` and that week counts toward streaks. This supersedes the §3.1 rule that excluded a partial first week. | Product decision (Phase 5 brief). A user starting on Friday can earn their first week instead of waiting 10 days for a streak. Examples in docs/STREAK_RULES.md. | Accepted |
| ADR-039 | **Completion date errors keep the approved codes and add a reason:** future dates and dates before `start_date` → 422 `DATE_NOT_COMPLETABLE` with `details.reason` `DATE_IN_FUTURE` / `BEFORE_START_DATE`. An unscheduled weekday → 422 `DATE_NOT_SCHEDULED`. | The codes are the approved frontend contract (§3.1). The reason gives clients the finer distinction the Phase 5 brief asked for without a breaking rename. | Accepted |
| ADR-040 | **Daily overview and history semantics:** for `weekly_target`, a day's status is `completed` when done that day **or** when its week already met the target. Streaks in `/today` are always as of today, whatever date is viewed. `/today` uses exactly two queries (habits, then all completions from the earliest start date). `GET /completions` returns the requesting user's own completions in the workspace, archived habits included. Marking is `INSERT … ON CONFLICT DO NOTHING` + SELECT, under a `FOR SHARE` lock on the habit; a PUT with a note on an existing completion updates the note. | The dashboard shows nothing left to do once a weekly target is met. The query count stays fixed regardless of habit count (verified by a query-counting test). The insert pattern is race-safe without retries (5 concurrent PUTs → one row). | Accepted |
| ADR-041 | **Analytics semantics:** a scheduled instance is a day (daily/weekdays) or an ISO week (weekly_target). Today is counted only once completed, and the current week only once met. Archived habits are evaluated up to their archive date and included by default (`includeArchived=false` hides them); they never appear in `today`. Weeks overlapping the range start are included. The `daily` series and heatmap count day-based habits only. Rates are fractions with 4 decimals (`percent` stays 0–100). All analytics endpoints run exactly two queries and aggregate in memory with pure functions. | Rates never punish in-progress or untracked time (the PRD principle) and stay ≤ 1 with a defined denominator. A fixed query count keeps the dashboard fast as habits grow (verified by a query-counting test). | Accepted |
| ADR-042 | **Notification delivery abstraction:** everything sends through `dispatchNotification()` (`services/notifications/`). It reads `notification_preferences` (`reminders: false` mutes reminders on every channel; `inApp: false` skips the inbox) and calls each enabled `NotificationChannel`. First release has only `InAppChannel`, which inserts with `ON CONFLICT (dedupe_key) DO NOTHING`. Push and email are later subclasses registered in `DEFAULT_CHANNELS`. | Producers (scheduler, milestones) never depend on delivery details, so push and email need no changes to them. Database-level dedupe makes sends exactly-once across restarts and multiple instances. | Accepted |
| ADR-043 | **Reminder scheduler:** a node-cron tick every minute, started only from `server.js` (never under `NODE_ENV=test`, or when `REMINDERS_ENABLED=false`), with `noOverlap`. Each tick computes each user timezone's local date and time with **Luxon** (not SQL `AT TIME ZONE`), then fetches the matching enabled reminders in one query: 4 queries per tick regardless of size. Each notification's dedupe key is `reminder:{id}:{localDate}`. Exact-minute match: a minute the server was down is not caught up. Daily housekeeping at 03:15 UTC deletes expired sessions and **all** notifications older than 90 days (§3.1), not only read ones. | Luxon keeps "today" identical to the rest of the app, and an unknown zone can't break the query for everyone. Purging unread notifications too keeps the table bounded; a reminder nobody opened in 90 days has no value. | Accepted |
| ADR-044 | **Reminder, due and milestone rules:** reminders are per user and per habit: at most 5 (422 `REMINDER_LIMIT_REACHED`), one per time (409 `REMINDER_DUPLICATE`), weekdays within a weekdays habit's schedule (422 `REMINDER_WEEKDAYS_NOT_SCHEDULED`), none added to archived habits (409). `isDue` = viewing today, the habit is pending, and an applicable reminder time has passed. Streak milestones (7/30/100/365, days or weeks) fire when a **new** completion makes the current streak cross one; only the highest crossed is sent, once per run (key includes the run's start date). The copy is encouraging, and missed days never notify. | Bounded, predictable reminder setup. Milestones can't be farmed by unmarking and re-marking a day, but a new run after a break is celebrated again (PRD: no punitive feedback). | Accepted |
| ADR-045 | **Frontend stack:** JavaScript (not TypeScript), React 19 + Vite 8, React Router 7 (data router), TanStack Query 5, Tailwind CSS 4 (configured in CSS via `@tailwindcss/vite`), axios, react-hook-form + Zod 4 (`@hookform/resolvers` **pinned to 5.x**), Luxon, Recharts, clsx, lucide-react. Dev: Vitest 5 + jsdom + Testing Library (+ `@testing-library/jest-dom`) + MSW 3, ESLint 10 (+ `eslint-plugin-react-hooks`), Prettier. **No** `eslint-plugin-jsx-a11y`. | JavaScript matches the backend and the junior-friendly comment standard. Resolvers 6.x declares conflicting optional peers (Effect 3 vs 4) and would need `--legacy-peer-deps`; 5.9 has no such peers and supports Zod 4. jsx-a11y doesn't support ESLint 10 yet; accessibility is enforced by the components themselves and by tests that query by ARIA role. | Accepted |
| ADR-046 | **Frontend architecture:** one axios client (`services/apiClient.js`) adds `withCredentials`, `X-CSRF-Token` on non-GET (fetching `/auth/csrf` first if the cookie is missing), `X-Workspace-Id`, and normalises errors to `ApiError { status, code, message, details }`. Auth state = the `/auth/me` query (null = anonymous). The 401 handler acts only when a session existed and was lost: clear the cache and go to `/login?returnTo=…` (same-site paths only). Vite proxies `/api` in development, so cookies are first-party. Habit status colours never use red for "missed". | One place for security headers and error shapes. The server stays the source of truth for the session (no token in JS storage). Guarding `returnTo` prevents open redirects. The colours follow the PRD's no-punitive-feedback principle. | Accepted |
| ADR-047 | **Daily experience UX rules:** ticking a habit is optimistic (the `/today` cache is updated at once via `optimistic.js`, rolled back by applying the INVERSE toggle on error, then today/habits/analytics are refetched). Each habit's in-flight state is keyed in the mutation cache (`['toggle-completion', habitId, date]`, read with `useIsMutating`) so it survives the row moving between groups. Toggles use `aria-pressed` with a constant label, and `aria-disabled` (not `disabled`) while pending or read-only so focus can stay on them and is restored after the row moves. The selected day lives in `?date=`. "Not scheduled today" comes from the active habit list minus `/today`. Delete offers "Archive instead" first. Reordering uses Move up/down buttons (keyboard and screen-reader friendly) rather than drag only. On phones toasts appear at the top, never over the thumb zone. | The PRD's "a completion takes seconds" and accessibility requirements. Snapshot rollback would erase another row ticked meanwhile; a disabled button can't hold focus. The toast position came from an E2E failure where a bottom toast covered the form's submit button at 375 px. | Accepted |
| ADR-048 | **Playwright E2E** (`frontend/e2e/`, `npm run test:e2e`): starts its own API (port 3100, NODE_ENV=test, `habitflow_test`) and Vite (port 5174), migrates and seeds plans in a global setup, and runs every test on desktop (1280 px) and a 375 px phone, asserting no horizontal scroll and saving screenshots to `test-results/screens/`. | Verifies the real browser loop at both sizes (the Phase 9 "done when") without touching dev data or the ports of a running `npm run dev`. Playwright was already in the approved stack. | Accepted |
